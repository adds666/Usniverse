## 3. Core problems encountered (DO NOT SKIP)

### 3.1 Docker inside unprivileged LXC is NOT plug-and-play

Symptoms encountered repeatedly:
- `OCI runtime create failed`
- `permission denied: sysctl net.ipv4.ip_unprivileged_port_start`
- `fuse-overlayfs: device not found`
- Containers created but **fail at start**
- Docker appears installed and healthy, but containers will not run

These errors are **not Docker bugs**.  
They are **Proxmox LXC confinement issues**.

---

## 4. The actual root causes (important)

### Root cause 1 - `/dev/fuse` not available to container

Docker defaults to overlayfs. Inside unprivileged LXC, overlayfs is blocked, so Docker falls back to `fuse-overlayfs`.

But:
- Proxmox host must load `fuse`
- LXC must explicitly allow `/dev/fuse`

### Root cause 2 - AppArmor + proc/sys restrictions

Docker containers expect:
- writable `/proc`
- writable `/sys`
- ability to read certain sysctls at container init

Unprivileged LXC blocks this unless explicitly relaxed.

### Root cause 3 - Changing LXC privilege after creation is impossible

- You cannot flip unprivileged -> privileged
- Attempts like `pct set 111 --unprivileged 0` will fail
- The fix must work within unprivileged constraints

## 5. The ONLY configuration that works (authoritative)

### 5.1 Proxmox host requirements

On the **Proxmox host**:
- Kernel module `fuse` must be loaded
- It must persist across reboots

Required:

```bash
modprobe fuse
echo fuse > /etc/modules-load.d/fuse.conf
```

### 5.2 CT111 LXC config (mandatory)

File:

```text
/etc/pve/lxc/111.conf
```

Must contain all of the following (order not important):

```ini
lxc.cgroup2.devices.allow: c 10:229 rwm
lxc.mount.entry: /dev/fuse dev/fuse none bind,create=file
lxc.apparmor.profile: unconfined
lxc.mount.auto: proc:rw sys:rw
features: nesting=1,keyctl=1
```

Without **every one** of these, Docker containers may:
- pull images
- create containers
- fail silently at start

### 5.3 Restart requirement

After modifying LXC config (on the Proxmox host):

```bash
pct stop 111
pct start 111
```

A reboot **inside** the container is not sufficient.

## 7. Jellyfin deployment (current state)

### 7.1 Directories

Inside CT111:

```text
/opt/jellyfin
/opt/jellyfin/config
/data/media
/data/transcode
```

### 7.2 docker-compose.yml (known-good)

```yaml
services:
  jellyfin:
    image: lscr.io/linuxserver/jellyfin:latest
    container_name: jellyfin
    environment:
      - PUID=1000
      - PGID=1000
      - TZ=Europe/London
    volumes:
      - /opt/jellyfin/config:/config
      - /data/media:/data/media
      - /data/transcode:/transcode
    ports:
      - "8096:8096"
    restart: unless-stopped
```

### 7.3 Bring-up command

From inside CT111:

```bash
cd /opt/jellyfin
docker compose up -d
```

If any LXC permissions are wrong, this command will fail with OCI runtime errors.

## 8. SSH and Ansible lessons (do not repeat mistakes)

### 8.1 SSH failures were not network issues

Most SSH failures were caused by:
- root SSH keys missing inside CT
- host key mismatch after container recreation
- wrong Ansible user (admin vs root)

### 8.2 Rule going forward

- Bootstrap CT access via Proxmox (`pct enter`)
- Install SSH keys manually once
- Only then rely on Ansible
- Do **not** debug Docker while SSH access is unstable

---

## 9. What NOT to do (hard-earned)

Do NOT:
- try to switch CT111 to privileged
- assume Docker errors mean Docker is broken
- assume `docker info` being clean means containers will run
- debug Jellyfin config before fixing LXC confinement
- reinstall Docker repeatedly (wastes time)

## 11. Single sentence summary (memorise this)

Docker inside unprivileged Proxmox LXC only works if `/dev/fuse`, AppArmor, proc/sys mounts, and cgroup permissions are explicitly relaxed - otherwise containers will fail at runtime even though Docker itself appears healthy.
